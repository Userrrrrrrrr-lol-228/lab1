# Lab API — лабораторные анализы

REST-сервис учёта лабораторных анализов (Spring Boot + PostgreSQL).
Заказчик сдаёт **образец**, к образцу назначаются **анализы** по выбранной **методике**,
в рамках анализа записываются **измерения**. По подтверждённым измерениям считается результат.

## Сущности и связи
- `users` 1—N `samples` (заказчик → его образцы)
- `samples` 1—N `analyses` (образец → анализы)
- `analysis_methods` 1—N `analyses` (методика → анализы по ней)
- `analyses` 1—N `measurements` (анализ → измерения)

Удаление родителя каскадно удаляет дочерние записи (`ON DELETE CASCADE`).
Ограничения в БД: `NOT NULL`, внешние ключи, `CHECK` на статусы и на `min_value < max_value`,
`UNIQUE` на имя методики и на пару (образец, методика).

Статусы: образец `NEW → IN_ANALYSIS → DONE | REJECTED`,
анализ `NEW → IN_PROGRESS → DONE | FAILED`, или `CANCELLED`.

## Запуск
```bash
cp .env.example .env        # поменяй пароли
docker compose up -d        # Postgres + таблицы + тестовые данные + пользователь app_user
./mvnw spring-boot:run      # приложение на :8080
```
Приложение подключается к БД под `app_user`, у которого есть только SELECT/INSERT/UPDATE/DELETE.
Чтобы пересоздать БД с нуля: `docker compose down -v` (обязательно после обновления до задания 5 — добавлена таблица `user_sessions`).
В `.env` нужно добавить `JWT_SECRET` (см. `.env.example`).

## CRUD
`/api/users`, `/api/analysis-methods`, `/api/samples`, `/api/analyses`, `/api/measurements`
(GET, GET /{id}, POST, PATCH /{id}, DELETE /{id}).

## Бизнес-операции
| Операция | Что делает | Когда запрещена (409) |
|---|---|---|
| `POST /api/analyses/{id}/start` | анализ → `IN_PROGRESS`, образец → `IN_ANALYSIS` | анализ не `NEW`; образец закрыт; материал образца не подходит методике |
| `POST /api/analyses/{id}/measurements` `{"value": 7.0}` | добавляет измерение | анализ не `IN_PROGRESS`; значение вне `min..max` методики |
| `POST /api/measurements/{id}/confirm` | подтверждает измерение | анализ не `IN_PROGRESS`; уже подтверждено |
| `POST /api/analyses/{id}/complete` | считает среднее по подтверждённым; разброс > `maxSpread` → `FAILED`, иначе `DONE`; если все анализы образца `DONE` — образец `DONE` | анализ не `IN_PROGRESS`; подтверждённых измерений меньше 2 |
| `POST /api/samples/{id}/reject` | образец → `REJECTED`, его незавершённые анализы → `CANCELLED` | образец уже `DONE` или `REJECTED` |

Каждая операция выполняется в одной транзакции, данные остаются согласованными.

## Безопасность (Spring Security + JWT)
Аутентификация по JWT (HS256), без серверных HTTP-сессий и без cookie, поэтому CSRF-токен больше не нужен.
Пароли хранятся в БД в виде BCrypt-хеша.

| Endpoint | Тело запроса | Успех | Ошибки |
|---|---|---|---|
| `POST /auth/login` | `{"username", "password", "deviceId"?}` | 200 + пара | 401 неверные данные / заблокирован, 400 нет поля |
| `POST /auth/register` | `{"name", "username", "password", "deviceId"?}` | 201 + пара | 400 валидация, 409 логин занят |
| `POST /auth/refresh` | `{"refreshToken"}` | 200 + новая пара | 400 нет поля, 401 токен/сессия недействительны |

Успешный ответ: `{"accessToken": "...", "refreshToken": "..."}`. Access передаётся в заголовке
`Authorization: Bearer <accessToken>`, refresh — только в JSON-теле `/auth/refresh` (access там не нужен).

**Токены.** Оба — JWT с claims `sub` (логин), `jti` (новый UUID при каждой выдаче), `iat`, `exp`, `type`
(`access` / `refresh`); в access ещё `role`. Проверяются подпись, алгоритм HS256, срок, обязательные claims и `type`:
фильтр принимает только `access`, `/auth/refresh` — только `refresh`. Время жизни: `jwt.access-ttl` (15m) и
`jwt.refresh-ttl` (7d) в `application.yml`, секрет — `JWT_SECRET` в `.env` (не короче 32 байт).

**Сессии** (таблица `user_sessions`, одна строка = одна пара токенов, статус `ACTIVE` / `USED` / `REVOKED`):
- вход и регистрация создают сессию `ACTIVE`; пара возвращается только после её записи в БД, а регистрация
  и сессия создаются в одной транзакции;
- обновление в одной транзакции блокирует строку (`SELECT ... FOR UPDATE`), проверяет владельца (`sub`),
  пользователя, статус `ACTIVE` и `refresh_token_expiry > now`, переводит старую сессию в `USED` и создаёт новую
  `ACTIVE` с тем же `deviceId`. Из двух параллельных обменов одного refresh успешен только один;
- повторное предъявление ещё не истёкшего `USED` refresh переводит сессию в `REVOKED` (это изменение сохраняется)
  и возвращает 401; отозванная сессия тоже даёт 401;
- ошибка записи новой сессии откатывает всю операцию.

Роль `app_user` имеет на `user_sessions` только `SELECT, INSERT, UPDATE`.
Проверить статус сессии (только LAB): `POST /api/sessions/lookup` `{"refreshToken"}`, токены в ответе не возвращаются.
Посмотреть в БД: `SELECT username, device_id, status, access_token_expiry, refresh_token_expiry FROM user_sessions;`

`GET /api/auth/me` возвращает текущего пользователя (защищённый endpoint). Пароль в ответах не возвращается никогда.
Регистрация: пароль не короче 8 символов, с буквами и цифрами; пользователь всегда получает роль `CUSTOMER`,
переданное поле `role` игнорируется.

**Состояние учётной записи:** `enabled = false` означает, что пользователь заблокирован и войти не может (401).
Блокирует лаборант: `PATCH /api/users/{id}` `{"enabled": false}`.

**Роли**
| Роль | Что может |
|---|---|
| `CUSTOMER` (заказчик) | смотреть методики; сдать образец **от своего имени**; смотреть и отклонять **только свои** образцы |
| `LAB` (лаборант) | всё: CRUD всех сущностей, все бизнес-операции, управление пользователями |

Доступ к URL задаётся в `SecurityFilterChain`, а проверки, зависящие от контекста (чей это образец), — в `@PreAuthorize`.
Бизнес-ограничения действуют для всех ролей: например, заказчик не может отклонить свой образец, если тот уже `DONE`/`REJECTED` (409).

**Ответы при ошибках** (`{"error": "..."}`, без внутренних подробностей):
`401` — нет/неверный access-токен, неверный пароль, недействительный refresh или учётная запись заблокирована;
`403` — недостаточно прав; `400`/`409` — нарушение правил валидации/бизнес-логики; `404` — не найдено.

Тестовые пользователи: `lab / Lab12345` (LAB), `ivan / Ivan12345`, `anna / Anna12345` (CUSTOMER), `blocked / Blocked123` (заблокирован).

## Тесты
`./mvnw test` — интеграционные тесты на встроенном PostgreSQL (Docker не нужен): вход/обновление/повторное
использование refresh, ошибки 400/401/409, параллельный refresh, откат при ошибке записи сессии.

## Postman
Импортируй `postman/lab-api.postman_collection.json` и запусти коллекцию целиком (Runner или `postman collection run`):
0. JWT — вход `lab` (сессия `ACTIVE`), защищённый endpoint с access, refresh (старая `USED`, новая `ACTIVE`),
   повторный refresh (401, сессия `REVOKED`), неверные токены и учётные данные, регистрация (201 + пара, 409, 400),
1. CRUD — создаёт данные по каждой сущности (от имени `lab`),
2. Бизнес-операции — сценарий от запуска анализа до завершения и отклонения, включая запрещённые случаи,
3. Права заказчика — что зарегистрированный заказчик может и чего не может, блокировка учётной записи,
4. Удаление.

Авторизация коллекции — Bearer `{{accessToken}}` (access пользователя `lab`, его сохраняют запросы входа и refresh),
папка 3 — Bearer `{{customerAccess}}` нового заказчика.
